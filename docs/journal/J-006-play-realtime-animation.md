# J-006 · 실제 속도 재생 — 핀 상승과 로봇 성형을 시간축에 올리다

> **Grasshopper 안에서는 애니메이션이 안 된다.** GH는 입력이 바뀔 때 한 번 계산하고 멈추고,
> 타이머로 재계산을 걸면 매 프레임 IK 체인 1,175개가 다시 돈다.
> 그래서 재생을 GH 밖으로 뺐다 — `DisplayConduit` + WinForms 타이머를 `sticky`에 붙잡아 두는 구조.
> **실측 배속 오차 0.5%**, 프레임당 그리기 0.2~0.8 ms.
> 그리고 이 작업에서 사이클 타임 모델이 틀려 있었다는 것이 드러났다.

---

## DECISION-01 재생은 GH가 아니라 컨듀잇이 한다 ★★

- **기각한 대안 1 — 타이머로 `ExpireSolution`:** 프레임마다 상류 전체가 다시 계산된다.
  이 문서의 체인은 IK 1,175 타겟이라 한 번 도는 데 수 초다. 실시간이 불가능하다.
- **기각한 대안 2 — 프레임을 미리 다 구워 GH 출력으로 내고 슬라이더로 넘기기:**
  사람이 슬라이더를 끄는 속도가 곧 재생 속도가 되어 "실제 속도"라는 요구를 못 만족한다.
  (스크럽 용도로는 유용하므로 `play=False`일 때의 동작으로 남겼다.)
- **채택:** 계산은 한 번, 표시는 컨듀잇. 시간은 `Stopwatch`가 준다.

  | 층 | 담당 |
  |---|---|
  | `adaptive_mold/src/playback.py` | 시간만 계산 (타임라인·보간). Rhino.Geometry 외 의존 없음 |
  | `gh_components/gh_scripts/AMv1_Play.py` | 컨듀잇·타이머 수명 관리, 그리기 |

  시간 계산을 분리해 둔 덕에 **GH 없이 단위 테스트가 된다** (PROCEDURE-01).

## FACT-01 세 전제를 먼저 실측했다 ★

코드를 쓰기 전에 확인한 것 — 하나라도 안 되면 DECISION-01이 성립하지 않는다.

| 전제 | 결과 (Rhino 8.33, IronPython 2.7) |
|---|---|
| `Rhino.Display.DisplayConduit` 상속 | 된다 |
| 인스턴스를 `scriptcontext.sticky`로 솔루션 사이 유지 | 된다 (4초 뒤에도 살아 있음) |
| WinForms `Timer`가 UI 스레드에서 Tick | 된다 (2초에 44틱) |

- **측정 방법:** 틱 카운터를 sticky에 두고 브리지 호출을 2초 간격으로 두 번 — **"예외가 없다"가
  아니라 "숫자가 늘었다"로 판정.** 컨듀잇은 예외 없이 조용히 안 그리는 실패 방식이 있다.
- **`System.Timers.Timer`를 쓰지 않은 이유:** 스레드풀에서 돌아 UI 스레드 밖에서 `Redraw`를
  호출하게 된다. WinForms 타이머는 UI 스레드에서 Tick한다.

## FACT-02 사이클 타임 모델이 틀려 있었다 — 성형은 관절 속도로 돌지 않는다 ★★

`robot.cycle_time()`은 모든 구간을 **관절 최대 속도**로 계산한다. 공중 이동에는 맞지만
성형 구간에는 틀리다 — 롤러가 가열 판재를 눌러 앉히는 속도는 로봇의 능력이 아니라 **공정이
정한다.** 그대로 쓰면 애니메이션이 실제보다 훨씬 빠르다.

    성형(form)  dt = max(거리/feed, 관절시간)     <- 느린 쪽이 실제
    공중(air)   dt =      관절시간

- **`max`를 취하는 이유:** feed가 빨라도 로봇이 그 자세 변화를 그 시간에 못 만들면 못 간다.
- **실측 (feed 50 mm/s, joint_scale 0.25, 1,175 타겟):**

  | | 구간 수 | 시간 |
  |---|---|---|
  | 이송 지배 | 1,046 | 564.1 초 |
  | 관절 지배 | 128 | 22.9 초 |
  | 핀 상승 (최대 행정 244 mm @ 50 mm/s) | — | 4.9 초 |
  | 정지 | — | 1.0 초 |
  | **합계** | | **592.8 초 (9.9 분)** |

- **대조:** 같은 경로를 `cycle_time()`으로 재면 **42.9초**였다. 13.8배 차이다.
  기존 값이 "가감속 무시한 하한"이라는 단서는 붙어 있었지만, 하한이라기보다 **다른 것을
  재고 있었다.** 성형 공정 시간을 로봇 이동 시간으로 재고 있었던 것.
- **구간 종류는 '도착 타겟'이 정한다.** approach→form의 첫 구간을 form으로 세어 이송 속도로
  다룬다 — 접촉 순간에 내려꽂지 않는 쪽이 안전하다. 경계를 어디에 붙일지는 임의 선택이므로
  테스트에 그 의도를 적어 두었다(`test_kind_of_destination_decides`).
- **미검증:** `pin_speed` 50 mm/s와 `feed` 50 mm/s는 **가정치**다. 실제 스펙으로 바꾸면
  전체 시간이 그대로 비례해 바뀐다. 가감속은 여전히 무시한다(축별 가속도 한계가 데이터시트에 없다).

## FACT-03 프레임 예산은 넉넉하고, 병목은 타이머 해상도다 ★

- **측정값:** 프레임당 그리기 **0.17~0.76 ms**. 요청 25 fps에 **실측 21.2 fps**.
- **원인:** Windows 타이머는 시스템 틱 **15.625 ms** 배수로 스냅된다.
  40 ms 요청 → 46.875 ms → 21.33 Hz (실측 21.2와 일치).
  **그리기가 느려서가 아니다** — 0.3 ms짜리 작업이 46 ms 간격으로 불린다.
- **`PostDrawObjects`는 틱당 1.7~2.1회 불린다** (열린 뷰포트 수). 그래서 draws로 fps를
  계산하면 부풀어 보인다 — 처음에 21.2 fps를 36.7로 표시하고 있었다. 틱으로 세도록 고쳤다.
- **함의:** Brep이 아니라 선·폴리라인으로 그린다는 원칙은 유지하되, 여유가 크므로 표시를
  더 얹을 수 있다. 타겟 1,000개 폴리라인이 프레임 비용의 대부분이다(`show_path`로 끌 수 있다).

## TRAP-01 자기 출력 프리뷰가 재생을 덮는다 ★★

- **증상:** 재생이 도는데 화면 바닥에 납작한 격자가 겹쳐 그려져 있다.
- **원인:** 이 컴포넌트의 `pins`·`deck` 출력은 **`t` 시점 형상**이다. 재생 중에는 `t`가
  고정이므로 GH 프리뷰가 **틀린 그림을 계속 그린다** (재생을 t=0에서 시작하면 z=0의 격자).
- **해결:** 재생 중 `ghenv.Component.Hidden = True`. `solo=True`면 다른 컴포넌트도 같이 끈다
  (핀 Brep·강선·법선 화살표·롤러선이 화면을 덮는 것도 실측으로 확인).
  **끈 것을 (객체, 원래값)으로 기억해 teardown에서 되돌린다** — 안 되돌리면 재생을 멈춘 뒤
  캔버스가 빈 화면으로 남는다.
- **재발 조건:** 컨듀잇으로 그리면서 같은 형상을 출력으로도 내는 컴포넌트를 만들 때마다.

## TRAP-02 컨듀잇을 정리하지 않으면 쌓인다 ★

- **증상:** 슬라이더를 몇 번 만진 뒤 화면에 여러 프레임이 겹쳐 보이고 CPU가 오른다.
- **원인:** GH는 입력이 바뀔 때마다 코드를 다시 실행한다. 매번 새 컨듀잇·새 타이머가 생긴다.
- **해결:** **스크립트 맨 위에서 먼저 teardown.** sticky 키에 컴포넌트 `InstanceGuid`를 붙여
  컴포넌트를 여러 개 놓아도 서로의 타이머를 죽이지 않게 했다.
- **`CalculateBoundingBox`를 빼먹지 말 것.** 없으면 그린 것이 뷰 클리핑에 잘리고 ZoomExtents가
  반응하지 않는다 — 카메라가 우리 형상을 모르기 때문이다.

## TRAP-03 기본값이 두 컴포넌트에 흩어져 있었다 ★

- **증상 가능성:** `AMv1 Robot`은 `robot_base`가 비면 타겟 박스 중심에서 −X로 1900 mm에
  베이스를 잡는다. `AMv1 Play`가 그것을 모르면 로봇을 원점에 그린다 —
  **화면은 그럴듯하고 계산과 다른 위치다.**
- **해결:** `robot.default_base_plane()` 한 곳으로 올리고 두 컴포넌트가 같이 쓴다.
  실측 확인: Play가 보고한 베이스 원점 `(-1400, 500, 0)` = Robot이 쓰는 값.
- **일반화:** 표시 컴포넌트와 계산 컴포넌트가 같은 기본값을 각자 갖고 있으면 한쪽만 고쳐도
  아무 오류가 안 난다. 기본값은 코어에 둔다.

## FACT-04 `.gh`가 툴팁을 못 지킨다는 것이 재시작으로 다시 확인됐다

- 지난 세션 끝에 `apply_param_docs.py --check`가 **0 차이**였다. 오늘 Rhino를 새로 켠 뒤 적용을
  돌리니 **Inspect 32 / RollerPath 21 / Robot 14 / PathFrames 14 = 81개가 다시 차이**로 나왔다.
- 즉 **재시작 한 번이면 전부 날아간다.** `apply_param_docs.py`는 편의 도구가 아니라 문서를
  열 때마다 돌리는 정상 절차다. (현재 정본 112개 = Play 27개 추가.)

## TRAP-04 코드를 밀어넣으면 그 컴포넌트의 툴팁이 지워진다 ★★

- **측정:** `--check`가 **0 차이**인 상태에서 `AMv1 Robot`에만 `gh-set-code`를 했다.
  직후 `--check` → **Robot만 14개 차이**(설명 2,000여 자 → 403자), 나머지 4개는 0.
  다시 적용하니 Robot 14개만 적용됐다. 원인이 코드 push라는 것이 이보다 깔끔하게 나올 수 없다.
- **원인 추정:** GhPython이 `Code`를 파싱해 파라미터를 정비하면서 `Description`을 기본값으로
  되돌린다. (내부 동작은 미확인.)
- **해결 = 절차:** `gh-set-code` 뒤에는 **항상** `apply_param_docs.py`를 돌린다.
- **재발 조건:** 컴포넌트 코드를 고칠 때마다. 즉 개발 중에는 매번이다.
- **놓치기 쉬운 이유:** 코드 push는 "성공"으로 보고되고, 캔버스도 정상이며, 계산도 맞는다.
  잃은 것은 마우스를 올렸을 때만 보이는 것이라 며칠 뒤에 발견된다.

## TRAP-05 `GH_DocumentIO`를 브리지에서 부르면 응답이 사라진다 (작업은 된다) ★★

- **증상:** `SaveQuiet`(또는 `Open`)을 브리지로 호출하면 결과 파일이 생기지 않아 실패로 보인다.
  **그런데 디스크는 이미 바뀌어 있다.**
- **왜 위험한가:** 성공을 실패로 오인해 같은 작업을 반복하게 된다. 저장이라면 두 번 해도
  무해하지만, 되돌릴 수 없는 작업이면 두 번 하는 것이 사고가 된다.
- **해결:** `run-file`(CPython 3) 경로로 태우고 스크립트가 로그를 직접 쓴다 —
  `adaptive_mold/tools/save_gh_doc.py`.
- **원인 미확정.** 두 호출 모두 `GH_DocumentIO`였고, 같은 세션에서 다른 브리지 호출은 정상이었다.

**파일 크기로 판정하지 말 것.** 컴포넌트를 하나 늘리고 저장했는데 45,730 → 39,381 bytes로
**줄었다**(압축 + 설명 소실). 판정은 **다시 열어서 세는 것**으로 한다:

    객체 42개 / 스크립트 5개
    Inspect 15,261자 18·15 · RollerPath 5,785자 14·9 · Robot 5,726자 9·7
    PathFrames 3,839자 6·10 · Play 16,291자 20·8

- **부수 발견:** `SaveQuiet` 후에도 `IsModified`가 `True`로 남는다. 저장 여부의 근거로 쓸 수 없다.

## PROCEDURE-01 Rhino 의존 테스트를 밖에서 돌린다

`adaptive_mold/tests/*.py`는 `Rhino.Geometry`에 의존해 밖에서 못 돈다. ScriptEditor를 열어
Run을 누르면 자동화가 끊긴다. `dump_via_bridge.py`와 같은 경로를 도구로 만들었다.

```
python adaptive_mold/tools/run_tests_via_bridge.py playback
```

    밖(CPython 3) → 브리지 1999(IronPython 2.7) → RunScript → shebang대로 CPython 3

- **Rhino 콘솔 출력은 밖에서 보이지 않는다.** 테스트가 `tests/_<이름>_log.txt`를 쓰고 도구가
  그것을 읽는다. **로그를 먼저 지우므로**, 파일이 없으면 "통과"가 아니라 "실행되지 않았다"다.
- 결과: `test_playback.py` **18개 통과 / 0개 실패**.

## PROCEDURE-02 컴포넌트 생성을 멱등하게

`build_play_component.py`는 다시 돌려도 안전하다. 파라미터 순서가 정의와 다르면 전부 다시
만들지만, **그 전에 연결을 닉네임으로 기억해 두고 복원한다** (실측: 입력 하나 추가 시
18개 배선 자동 복원). 이게 없으면 파라미터를 늘릴 때마다 배선을 손으로 다시 해야 한다.

- `GhPython`의 `out`은 콘솔용 특수 출력이다 — 지우지 않고 앞에 남긴다.
- `IGH_Param`에 `RecipientCount`는 없다. `Recipients`를 열거할 것.

## 미해결

- `pin_speed`·`feed`가 가정치. 실제 스펙이 들어오면 전체 시간이 비례해 바뀐다.
- 가감속 미반영. 축별 가속도 한계가 데이터시트에 없다.
- 핀이 "동시에 출발해 각자 멈추는" 제어라고 가정했다. 전부 같은 시각에 도착하는 보간 이동이면
  모델을 고쳐야 한다 — 실물이 어느 쪽인지 확인되지 않았다.
- 판재를 올리고 가열하는 시간은 타임라인에 없다(`dwell`로 뭉뚱그렸다).
- 판재 자체의 변형은 그리지 않는다. 롤러가 지나간 자리를 표시하는 정도다 —
  변형 시뮬레이션은 다음 슬라이스.
