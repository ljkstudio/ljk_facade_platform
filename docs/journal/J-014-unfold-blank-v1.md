## TRAP-01 컴포넌트가 통째로 안 도는데 오류가 없다 ★★

- **증상:** `run` 을 켰는데 출력이 전부 비었다. solution 이 0.01초에 끝난다.
  경고는 `Input parameter props failed to collect data` 류가 입력마다 하나씩.
  오류(빨강) 표시는 없다.
- **원인:** 새 Script 컴포넌트의 입력 파라미터를 코드로 만들 때 `Optional` 을
  세우지 않으면 **안 물린 입력 하나가 컴포넌트 전체의 실행을 막는다.** 기본값을
  코드 쪽에서 주는 설계(`float(edge_mm or 40.0)`)와 정면으로 어긋난다.
- **해결:** `build_uf_components.py` 의 `make_param()` 에서 입력에 `Optional = True`.
  빌더 출력에 `opt=True` 를 찍어 눈으로 확인할 수 있게 했다.
- **재발 조건:** **파라미터를 코드로 만들 때마다.** 손으로 만든 파라미터는 GH 가
  기본을 Optional 로 잡아 주므로 이 함정은 자동화 경로에만 있다.

## TRAP-02 크기를 감춘 경고는 경고가 아니다 ★★

- **증상:** 정확한 가전개면인 원통에서 `성형 중 압축되는 요소 3120개 (전체 6281개).
  최대 σ = 1.0000` 이 떴다. 개수가 절반이라 심각해 보이는데 σ 는 1.0000 이다.
- **원인:** 문구가 `%.4f` 라 **반올림에 크기가 먹혔다.** 실제 압축은 0.001%
  (σ = 1.000014) — 수치 잔차다. 무시해도 되는 잔차와 진짜 주름(돔 6.6%)이
  **같은 문장으로 나온다.**
- **해결:** 압축률을 유효자리로 적는다 — `최대 압축 0.001% (σ = 1.000014)`.
  임계값(`WRINKLE_TOL = 1e-6`)은 올리지 않았다(DECISION-03).
- **재발 조건:** 판정 문구에 `%.4f` 를 쓸 때마다. **판정의 자릿수는 표시 취향이
  아니라 판정의 일부다.** 0 근처에서 갈리는 값이면 특히 그렇다.

> 이 함정이 위험한 이유는 반대 방향이라는 것이다. "미판정을 통과로 치지 않는다"는
> 원칙은 **놓치는 것**을 막지만, 이건 **무해한 것을 경고로 쳐서 진짜 경고를 묻는**
> 실패다. 한 번 이러면 그 경고는 그 뒤로 아무도 안 읽는다.

## TRAP-03 파이썬 리스트가 GH 항목으로 갈라지지 않는다

- **증상:** `warn` 출력을 패널에 물렸더니 `['[경고] 주름: …', '[미판정] 찢어짐: …']`
  로 대괄호와 따옴표째 한 줄에 찍혔다. 판정을 읽을 수가 없다.
- **원인:** Rhino 8 의 새 Script 컴포넌트는 파이썬 리스트를 GH 항목으로 풀어주지
  않는다. 구형 GhPython 과 다르다.
- **해결:** 어댑터에서 `"\n".join(warn)`. 시도했지만 안 통한 것 둘:
  - 출력 파라미터를 `GH_ParamAccess.list` 로 → `GH_ObjectWrapper(PyObject)` 하나로 나온다
  - 그 위에 `string` 힌트를 걸어 → 리스트를 통째로 문자열화한다 (**더 나빠진다**)
- **재발 조건:** 새 Script 컴포넌트에서 리스트를 출력할 때마다.

## DECISION-01 전처리를 넣고, 사전 분해는 여전히 안 쓴다

- **선택:** 야코비(대각) 전처리를 CG 에 넣는다.
- **근거:** cotangent 라플라시안은 삼각형 모양과 정점 차수에 따라 대각이 자릿수
  단위로 다르다. 실측 CG 8,616 → 4,194회, σ 는 소수 여섯째 자리까지 동일,
  골든 픽스처(상대오차 1e-6) 그대로.
- **기각한 대안:** **Cholesky 사전 분해.** `wrinkle_penalty = 1.0` 인 기본 경로에서는
  가중이 안 변해 행렬이 매 반복 같으므로 한 번 분해해 재사용할 수 있다 — 이론상
  가장 큰 이득이다. 버린 이유: 순수 파이썬으로 희소 Cholesky 를 쓰려면 채움
  억제(AMD 정렬)까지 따라와야 하고, 그건 이 단계에서 감당할 분량이 아니다.
  게다가 numpy 를 살리자 CG 가 0.17초로 떨어져 **분해로 벌 수 있는 절대량이
  사라졌다.**
- **뒤집을 조건:** 정점이 2만을 넘거나, `wrinkle_penalty > 1` 을 기본으로 쓰게 되어
  IRLS 로 행렬이 매 반복 바뀌는데도 느릴 때.

## DECISION-02 안쪽 허용치는 1e-9 까지만 — 가드를 팔지 않는다 ★

- **선택:** `CG_REL` 을 1e-11 → **1e-9**.
- **근거:** 바깥 루프는 에너지 상대변화 1e-6 에서 멈추는데 안쪽 선형계를 다섯 자리
  더 정확하게 풀고 있었다. 1e-9 에서 Δσmax 3.3e-11, 테스트 116개 전부 통과.
- **기각한 대안:** **1e-7.** 더 빠르다(전처리 포함 5.66 → 2.74 s). 버린 이유는
  속도가 아니라 **무엇을 파는가**다. 1e-7 은 두 가드를 깼다 —
  강체 불변(`abs=1e-6`)과 순수/numpy 두 경로 일치(`abs=1e-9`). 그 둘은 좌표계
  혼동과 백엔드 불일치를 잡는 방어선이고, **통과시키려고 허용치를 늘리는 것은
  속도를 산 게 아니라 방어선을 판 것**이다. numpy 로 이미 20배를 벌어 둔 상태라
  더 팔 이유도 없었다.
- **뒤집을 조건:** numpy 를 못 쓰는 환경이 상용 조건이 되고, 그때 가드의 허용치를
  `CG_REL` 에서 파생시키는 정리를 함께 하는 경우.

## DECISION-03 주름 임계값은 안 올린다. 대신 크기를 말한다

- **선택:** `WRINKLE_TOL = 1e-6` 유지. 문구가 압축률을 유효자리로 적게 한다.
- **근거:** 원통의 오탐(TRAP-02)은 임계값이 낮아서가 아니라 **읽는 사람이 크기를 볼
  수 없어서** 생긴다. 크기가 보이면 0.001% 는 사람이 무시한다.
- **기각한 대안:** 임계를 물리적 크기(예: 압축 0.1% = σ > 1.001)로 올리는 것.
  버린 이유: 판재·두께·성형 방식마다 다른 값을 **근거 없이 못 박게 된다.**
  `material.py` 가 막으려고 만든 '가짜 손잡이'와 같은 실패다 — 숫자가 있으면
  사람들은 그게 검증된 값이라고 믿는다.
- **뒤집을 조건:** 실제 성형 시험으로 "이 판재는 압축 X% 까지 주름 안 진다"가
  출처와 함께 나올 때. 그때는 임계가 아니라 **물성**으로 들어가야 한다.

## DECISION-04 정점 상한을 개수에서 시간 예산으로

- **선택:** `max_verts` 기본값을 백엔드 속도에서 거꾸로 계산한다(예산 3초 →
  numpy 8,108 / 순수 600). 거부 메시지에 **예상 시간**을 적는다.
- **근거:** 사용자가 겪는 것은 "정점 16,385개"가 아니라 "6초 동안 멈춘 Rhino"다.
  실측 6.14 s, 추정 6초로 맞았다. 예전 값 5,000 은 순수 파이썬 시절에 정해진
  것이라 **numpy 에서는 1.2초짜리 메쉬를 막고, 순수 파이썬에서는 25초짜리를
  통과시킨다.**
- **기각한 대안:** 상수를 그냥 20,000 으로 올리기. 버린 이유는 위와 같다 — 한
  숫자를 두 백엔드에 쓰면 한쪽은 과보호, 다른 쪽은 무방비가 된다.
- **뒤집을 조건:** 계산을 UI 스레드 밖으로 뺄 수 있게 되면 예산 자체가 의미를 잃는다.

## PROCEDURE-01 캔버스에 올린 컴포넌트를 검증하는 한 판

- **목적:** "캔버스가 멀쩡해 보인다"가 아니라 **출력값과 메시지로** 판정한다.
- **단계:**
  1. `python -m pytest unfold/tests -q` — 코어를 밖에서 먼저 고정한다
  2. `python unfold/tools/build_uf_components.py` — 파라미터·힌트·코드 push
  3. `python unfold/tools/apply_uf_param_docs.py` — **②가 툴팁을 지운다** (TRAP-04)
  4. `python unfold/tools/wire_uf_harness.py <패널> edge=… elong=…` — 입력을 물린다.
     Brep 참조는 걸고 나서 `ReferenceID` 를 되읽어 대조한다
  5. `python unfold/tools/run_uf_test.py` — 한 번 돌리고 `RuntimeMessages`·출력값·
     "평탄화 정점이 재단선 안에 다 들어갔는가"를 센다. 끝나면 `run` 을 다시 끈다
  6. `python unfold/tools/apply_uf_param_docs.py --check` — **0 차이**여야 한다
- **자동화 후보:** **예.** ②~⑤ 를 곡면 5종에 대해 한 번에 도는 스크립트가 다음 단계다.
  이번에 손으로 다섯 번 돌렸다.

## PROCEDURE-02 이론해로 전개를 검증하는 법

- **목적:** "그럴듯한 그림"이 아니라 아는 답과 대조한다.
- **단계:**
  1. **평면** — σ 가 정확히 1. 아니면 좌표계나 국소 프레임이 틀렸다
  2. **기울인 평면** — 역시 σ=1. 여기서만 깨지면 투영·정렬이 틀렸다
  3. **원통(가전개면)** — σ=1, 면적비 1. 여기서 변형이 나오면 솔버가 틀렸다
  4. **구면 캡** — 이론 상·하한 사이에 들어가는지 (`test_theory.py`)
  5. **안장** — 인장·압축이 함께 나오는지
- **자동화 후보:** **예.** 1~5 중 4는 이미 pytest 에 있고(골든 픽스처 포함),
  나머지는 Rhino 패널로 돌고 있다.

## 미해결

- **정사각 패널이 45° 돌아 나온다.** 주축 정렬인데 정사각형은 공분산이 등방이라
  방향이 자유롭다. 1200×1200 이 bbox 1697×1697. 계산은 맞지만 시트 활용률에
  불리하다. 최소면적 외접사각형 정렬을 넣을 것인가 — **네스팅과 함께 결정할 일**이다.
- **원통이 30회 상한까지 수렴 판정을 못 받는다.** 에너지 3.41e-05 에서 평평해지는데
  상대변화 판정에 안 걸린다(54회에 수렴). 절대 하한을 함께 볼 것인가.
- **툴팁이 화면에 실제로 뜨는지 확인 못 했다.** `Description` 과 `ToolTip` 두 속성에
  다 넣고 되읽기까지 했지만, 렌더 경로(`GH_TooltipDisplayEventArgs`)가 비공개
  생성자라 밖에서 태울 수 없다. 사람이 한 번 올려 봐야 한다.
- **UFv1 컴포넌트가 `AMv1_Inspect.gh` 안에 산다.** 별도 `.gh` 로 옮길지 미정.
