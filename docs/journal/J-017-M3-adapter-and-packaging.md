## TRAP-01 새 Rhino 세션에서 테스트가 0개인데 러너만 그것을 안다 ★★★

- **증상:** M3 를 시작하려고 기준선을 재니 97/97 이 아니라
  `total=0 passed=0 failed=0`. 결과 XML 의 어셈블리 스위트가
  `runstate="NotRunnable" site="SetUp"` 이고 사유는
  `Could not load file or assembly 'Microsoft.VisualStudio.TestPlatform.ObjectModel, Version=15.0.0.0'`.
- **원인:** `Microsoft.NET.Test.Sdk` 가 테스트 어셈블리에 `AutoGeneratedProgram`
  타입을 심는데 그 타입의 속성이 저 어셈블리에 있다. NUnit 은 어셈블리를 훑으며
  **모든 타입의 속성을 읽으므로** 하나라도 못 풀면 어셈블리 전체가 죽는다.
  `e29f4b5`(세션당 한 번만 돌던 문제)에서 `Assembly.LoadFrom` 을 커스텀
  `AssemblyLoadContext` 로 바꿨는데, **LoadFrom 이 해 주던 폴더 탐색이 같이
  사라졌다.** 커스텀 ALC 는 명시적으로 올린 것 말고는 기본 ALC 로만 떨어진다.
- **왜 그동안 안 드러났나:** `e29f4b5` 를 만든 세션에는 그 이전 실행의
  `LoadFrom` 이 기본 ALC 에 ObjectModel 을 이미 올려 둔 상태였다.
  **M2b 의 97/97 은 그 오염된 세션에서 측정된 값이다.** 새 세션에서 처음
  돌리면 터진다.
- **해결:** ALC 의 `Resolving` 에서 스테이지 폴더를 보게 했다(`1e0d963`).
  마지막 기회 훅이라 거기 없는 것(RhinoCommon·Grasshopper 처럼
  `ExcludeAssets=runtime` 인 것)은 그대로 기본 ALC 로 떨어진다.
  실측: `Resolving` 이 ObjectModel 과 그 의존 PlatformAbstractions 를 잡아 준다.
- **재발 조건:** 커스텀 ALC 로 어셈블리를 태우면서 **bin 에 있는 의존성이
  하나라도 늘 때마다.** 그리고 **긴 Rhino 세션에서 로더를 고친 뒤 새 세션으로
  검증하지 않을 때마다.**

**가장 위험한 부분은 0개가 실패로 보이지 않는다는 것이다.** 러너에 이미
`total == 0 → [실패]` 가드가 있어서 살았다. 그 가드가 없었으면 M3 전체를
"테스트 통과" 위에 쌓았을 것이다.

## TRAP-02 `params.ko.json` 의 `.ko.` 를 MSBuild 가 한국어 컬처로 읽는다 ★★★

- **증상:** `EmbeddedResource` 를 넣었는데 런타임에
  `GetManifestResourceStream` 이 null. `GetManifestResourceNames()` 는 0개.
- **진단이 어려운 이유:** 빌드가 **경고 0 오류 0** 이고,
  `dotnet msbuild -getItem:EmbeddedResource` 는 항목을 정상으로 보여 주며,
  `-v:detailed` 의 csc 명령줄에도 `/resource:..\..\docs\params.ko.json,...` 이
  멀쩡히 보인다. 증분 빌드를 의심해 `-t:Rebuild` 와 bin/obj 삭제까지 했지만
  결과가 같았다.
- **원인:** csc 가 **두 번** 돈다. `-v:detailed` 에서 `/out:` 을 같이 뽑아 보면
  두 번째가 `/out:obj\Debug\net7.0-windows\ko\AdaptiveMold.GH.resources.dll` 이다.
  MSBuild 의 `AssignCulture` 가 파일명의 `.ko.` 를 컬처로 해석해 리소스를
  본체가 아니라 **한국어 위성 어셈블리**로 보낸다.
- **해결:** `WithCulture="false"` 메타데이터. 실측 본체 **10,240 B → 55,296 B**,
  위성 `ko\...resources.dll` 49,152 B 소멸.
- **재발 조건:** 임베드하는 파일 이름에 **두 글자 문화권 코드처럼 보이는 마디**가
  있을 때마다 (`.ko.`·`.en.`·`.ja.`·`.de.` …). 우리 정본 파일명이 정확히 그렇다.

**진단을 대신 읽어 준 것은 Task 3 의 셋째 테스트였다** — "없는 이름에 예외를
던지지 않는다"가 로드 오류 메시지를 그대로 문자열로 돌려줘서, 실패 출력에
`임베드 리소스 ... 이 없다` 가 찍혔다. 조용히 던졌으면 GH 가 컴포넌트를
팔레트에서 뺐을 것이고 원인을 못 찾았을 것이다.

## TRAP-03 브리지에서 GH 를 부르면 로더가 굶는다 ★★★

- **증상:** `PlugIn.LoadPlugIn(GH guid)` 또는
  `RhinoApp.RunScript("_Grasshopper")` 를 브리지로 부르면 응답이 안 오고
  타임아웃(300 s / 600 s). 그 뒤 상태는 **편집기는 열려 있고
  (`DocumentEditor.Visible=True`, `ActiveCanvas` 있음) 라이브러리는 0** 이다.
  `ComponentServer.IsLoading == True` 인 채로 멈춘다. `LoadingExceptions` 는 0.
- **원인:** 브리지 스크립트가 UI 스레드에서 도는데 GH 로더는 같은 스레드가
  메시지를 처리해야 진행한다. 동기 호출이 스레드를 쥐고 있어 서로 기다린다.
- **해결:** **`RhinoApp.SendKeystrokes("Grasshopper", True)`** — 명령을 큐에
  넣고 즉시 반환하므로 스레드를 놓아준다. 이후 GH 가 정상 로드된다
  (실측 `libs=31 proxies=2329 IsLoading=False`).
- **재발 조건:** 브리지에서 **UI 를 띄우거나 플러그인을 로드하는 동기 API** 를
  부를 때마다. `GH_DocumentIO` 가 응답을 안 돌려주는 기존 함정(스킬 §5)과 같은
  뿌리다.

## TRAP-04 브리지는 "GH 로드됨"이라는데 화면은 모달에서 멈춰 있다 ★★★

- **증상:** TRAP-03 을 고친 뒤에도 라이브러리가 0. 브리지 `status` 는
  `grasshopper loaded`, 프로세스는 `Responding=True`, CPU 도 안 튄다.
  **지표로는 아무 문제가 없다.**
- **원인:** 화면에 GH `File Conflict` 모달이 떠 있었다. 개발 빌드
  (`bin\Debug\net7.0-windows\AdaptiveMold.GH.gha`, 58.4 KB, 당일 09:51)와
  **설치본 껍데기**(`packages\8.0\ljks-adaptive-mold\0.1.0\`, 8.2 KB, 전날 11:31)가
  같은 이름이라 어느 것을 Load 할지 묻고 있었다.
- **해결:** **왼쪽(개발 빌드) `Load`.** 각 쪽에 `Delete...` 가 `Load` 바로 위
  29 px 에 있으므로 좌표를 재고 누를 것 — `Delete` 는 파일을 지운다.
  이어서 `Select Grasshopper-Tekla Link Version`(Tekla 미실행)과
  `Unable to initialize the Grasshopper-Tekla live link`(우리는 `/netcore` 로
  띄우므로 당연)가 뜬다. 둘 다 확인만 누르면 된다.
- **재발 조건:** **`RHINO_PACKAGE_DIRS` 개발 빌드와 설치본이 공존할 때마다.**
  Task 12 에서 새 `.yak` 을 설치해도 같은 상황이 된다 — 개발 중에는 설치본을
  빼 두거나, 뜰 때마다 왼쪽 Load 를 누른다는 것을 알고 있을 것.

**판정 순서:** 로딩이 안 끝나면 ① `ComponentServer.IsLoading` ②
`LoadingExceptions` ③ **화면의 모달**. 지표만 보면 ③ 은 영원히 안 보인다.

## DECISION-01 어댑터 계약 검사는 NUnit 안에 둔다

- **선택:** `NUNIT`. Task 1 스파이크 통과 — 테스트 ALC 에서
  `new AMv1PinsComponent()` 가 된다(실측 `in=1 out=1 name="AMv1 Pins"`,
  당시는 아직 껍데기).
- **근거:** `Grasshopper` 는 `ExcludeAssets=runtime` 이라 bin 에 없고 기본
  ALC(=Rhino 가 로드한 것)로 떨어지는데, GH 플러그인이 로드돼 있으면 성립한다.
- **기각한 대안:** 브리지 스크립트(`check_param_docs.py`)로 옮기는 안.
  검사 내용은 같지만 Rhino·캔버스 상태에 매번 의존하게 되고, `dotnet build`
  직후 바로 못 돈다.
- **뒤집을 조건:** GH 로드를 테스트 전제로 두는 것이 CI 에서 불가능해지면.
  (러너에 `GH_LOADED` 검사를 넣어 두었으므로 그때는 조용히 0개가 아니라
  명시적 실패로 나온다.)

## DECISION-02 `AdaptiveMold.GH` 를 ALC 에 명시적으로 올린다

- **선택:** `Resolving` 폴더 탐색에 맡기지 않고 `Core` 와 같이 명시적
  `LoadFromAssemblyPath`.
- **근거:** ⑴ 확장자가 `.gha` 라 `.dll` 만 보는 폴더 탐색에 안 걸린다.
  ⑵ 더 중요한 것 — **캔버스가 열리면 GH 가 설치된 패키지의 같은 이름
  어셈블리를 기본 ALC 에 올린다.** `Resolving` 은 기본 ALC 실패 뒤에야 불리므로
  맡겨 두면 테스트가 **방금 빌드한 것이 아니라 낡은 설치본**에 붙는다.
- **기각한 대안:** `Resolving` 에서 `.gha` 확장자도 보게 하는 안 — 확장자
  문제는 풀리지만 위 ⑵ 가 그대로 남는다.
- **뒤집을 조건:** 설치본과 개발 빌드가 절대 공존하지 않는 환경이 되면.

## FACT-02 `AddDocument` 오버로드 셋, 브리지에서 쓸 수 있는 것은 둘

- **측정값:**
  ```
  AddDocument(GH_Document document)
  AddDocument(GH_Document document, Boolean& ref success)   <- IronPython 에서 못 부른다
  AddDocument(String filepath, Boolean makeActive)          <- .gh 를 열 때 이것
  ```

- **측정 방법:** `clr.GetClrType(GH.Kernel.GH_DocumentServer).GetMethods()`.

## 조사하다 스스로 밟은 것 하나

진단하려고 `bin\Debug` 의 `.gha` 를 **직접** `LoadFromAssemblyPath` 했더니
Rhino 가 파일을 잡고 놓지 않아 이후 빌드가 전부 막혔다
(`MSB3027 ... 파일이 "Rhino 8"에 의해 잠겨 있습니다`).
수집 가능(`isCollectible=True`) ALC 였는데 `GC.Collect` 로도
`AssemblyLoadContext.All` 순회 후 `Unload()` 로도 안 풀렸다.
**이름만 바꿔 비켜두면**(`AdaptiveMold.GH.gha.locked-01`) 빌드는 진행된다.

**조사할 때도 사본을 만들어 로드할 것** — 러너가 스테이지 복사본을 태우는
이유와 정확히 같다. 이건 J-015 에 이미 적혀 있던 함정이었다.
