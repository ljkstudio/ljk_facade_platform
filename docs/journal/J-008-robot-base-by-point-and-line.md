# J-008 · 로봇 위치를 점과 선으로 — 그리고 참조가 조용히 끊기는 자리

> Plane 을 GH 에서 조립하는 것보다 Rhino 에서 **점을 찍고 선을 긋는 것**이 빠르다.
> `robot_base`(평면) > `base_pt`/`base_dir`(점·선) > 자동, 세 단계 우선순위로 받는다.
> 일이 된 곳은 **참조**였다 — `Param_Line` 은 Rhino 객체를 참조할 수 없고,
> 그 실패가 **예외 없이 조용히** 일어난다.

---

## DECISION-01 베이스 결정은 한 함수에만 둔다 ★★

`robot.resolve_base_plane(robot_base, base_pt, base_dir, targets)` 하나가 판단하고
`AMv1 Robot`(계산)과 `AMv1 Play`(표시)가 **같은 함수를 부른다.**

J-006 TRAP-03 의 재발 방지다 — 표시와 계산이 각자 기본값을 갖고 있으면 한쪽만
고쳐도 **오류가 나지 않고** 로봇이 계산된 위치와 다른 곳에 그려진다.
두 컴포넌트가 자기 `info` 에 베이스 출처와 원점·방향을 적으므로 눈으로도 대조된다.

**규칙 (기각한 대안 포함):**

| 입력 | 결과 | 왜 |
|---|---|---|
| 선만 | 원점 = 선의 시작점, +X = 선 방향 | 선 하나로 위치·방향이 다 정해진다 — 가장 적게 만드는 길 |
| 점 + 선 | 원점 = 점, +X = 선 방향 | 선을 아무 데나 그어도 되게 |
| 점만 | +X = 타겟 중심을 향한다 | 월드 X 를 쓰는 것보다 쓸모 있다. 기각한 대안: 월드 X 고정 |
| 없음 | 자동 (타겟 중심에서 -X 1900) | 기존 동작 유지 |

**로봇은 항상 똑바로 선다.** 방향을 월드 XY 로 투영한다 — 원격 뷰포트에서 선을
그으면 의도와 달리 기울어지기 쉽고, 그대로 받으면 로봇이 넘어진 자세로 계산된다.
**투영이 일어나면 설명 문자열에 적어 돌려주므로 조용히 넘어가지 않는다.**
베이스를 실제로 기울이려면 `robot_base` 로 평면을 직접 준다(그 경로는 남겨 두었다).

## TRAP-01 `Param_Line` 은 Rhino 객체를 참조할 수 없다 ★★★

- **증상:** 점을 옮기면 로봇이 따라오는데 **선을 돌려도 방향이 안 바뀐다.**
  같은 코드로 같이 만들었고 배선도 되어 있고 값도 들어온다.
- **원인:** Rhino 에서 선은 **`LineCurve` 객체**다. `GH_Line` 은 참조 가능한
  지오메트리 타입이 아니라서 `ReferenceID` 를 넣어도 **예외 없이 버려진다.**

      volatile dir (1.000, 0.000)  ref=False
      persistent dir (1.000, 0.000)  refid=00000000-0000-0000-0000-000000000000

  값은 정상으로 보이고 배선도 정상이다. **끊긴 것은 참조뿐**이라 화면상 아무
  이상이 없다.
- **해결:** `Param_Curve` + `GH_Curve` 로 받는다. 컴포넌트 입력 힌트도
  `GH_CurveHint`. `robot._direction_of()` 가 Curve·Line·Vector 를 다 받으므로
  코어는 그대로다.
- **재발 조건:** Rhino 객체를 GH 파라미터로 참조하려 할 때마다. 참조가 되는 것은
  Rhino 에 **객체로 존재하는 타입**(Point, Curve, Surface, Brep, Mesh)이다.
  Line·Plane·Vector 같은 값 타입은 참조가 아니라 값으로만 들어간다.
- **교훈:** **예외가 없는 것을 성공의 근거로 쓰지 않는다.** 처음 판은
  `try/except` 로 감싸고 예외가 없으니 `"created/referenced"` 라고 보고했다.
  고친 판은 **넣은 뒤 다시 읽어** `ReferenceID` 가 맞는지 확인하고,
  아니면 `"VALUE ONLY (참조 실패)"` 라고 적는다.

## TRAP-02 이름이 그대로면 힌트를 고쳐도 반영되지 않는다 ★

- **증상:** 스펙의 힌트를 `GH_LineHint` → `GH_CurveHint` 로 고치고 빌드 도구를
  돌렸는데 캔버스에는 옛 힌트가 남았다.
- **원인:** 도구가 **닉네임 목록**을 비교해 추가·제거·재구성을 판단한다.
  이름이 그대로면 아무 일도 하지 않는다.
- **해결:** 힌트·접근방식(item/list) **동기화 단계를 따로** 두었다.
  현재 힌트 클래스 이름과 스펙을 비교해 다르면 갈아 끼우고 무엇을 고쳤는지 적는다.
- **재발 조건:** 선언형 스펙으로 기존 객체를 맞출 때마다. 비교 키에 없는 속성은
  절대 수렴하지 않는다.

## PROCEDURE-01 빌드 도구를 두 모드로 일반화했다

`build_play_component.py` → **`build_gh_components.py`** (컴포넌트별 스펙 표).
임시 스크립트로 파라미터를 붙이는 것을 그만두려 만들었다.

| 모드 | 하는 일 | 어디에 |
|---|---|---|
| `reorder=True` | 순서가 정의와 다르면 입력을 전부 다시 만든다. **연결은 닉네임으로 기억해 복원**(실측: 20개 복원) | `AMv1 Play` — 내가 처음부터 만든 것 |
| `reorder=False` | **추가·삭제만. 기존 파라미터는 손대지 않는다** | `AMv1 Robot` — `targets` 가 힌트 없는 상태로 잘 돌고 있어 다시 만들 이유가 없다 |

잘 돌고 있는 것을 "정리"하려고 다시 만드는 것이 가장 흔한 자해다. 그래서 기본을
`reorder=False` 로 두었다.

## PROCEDURE-02 점·선·배선을 한 번에 만든다

`make_robot_base_ref.py`:

1. Rhino 레이어 `robot_base` 에 점 `robot_base_pt`, 선 `robot_base_dir` 생성
2. GH `Param_Point` / `Param_Curve` 가 그 객체를 **참조**
3. `AMv1 Robot` 과 `AMv1 Play` 의 `base_pt`/`base_dir` 에 배선

**처음 위치를 지금 쓰이는 자동값과 같게 잡는다** — 타겟 중심에서 -X 1900,
방향은 중심을 향한다. 그래서 물리는 순간 로봇이 **튀지 않는다.**
튀면 무엇이 바뀐 것인지 알 수 없게 되고, 물린 것이 잘못됐는지 원래 값이 달랐는지
구분하지 못한다. **이름으로 찾아 재사용**하므로 다시 돌려도 객체가 늘지 않고
이미 옮겨 둔 위치를 덮어쓰지 않는다.

## 검증 근거

**참조가 살아 있다는 증거는 배선이 아니라 "옮겼을 때 숫자가 바뀌는 것"이다.**
Rhino 객체를 옮기고 돌린 뒤 두 컴포넌트를 읽었다.

| | 원점 | 방향 | max 오차 | 도달 실패 |
|---|---|---|---|---|
| 처음 | (-1400, 500, 0) | (1.00, 0.00) | 6.773 mm | 10 |
| **점 -300/+400, 선 20°** | **(-1700, 900, 0)** | **(0.94, 0.34)** | 403.670 mm | 246 |
| 되돌린 뒤 | (-1400, 500, 0) | (1.00, 0.00) | 6.773 mm | 10 |

- 방향 (0.94, 0.34) = (cos20°, sin20°) — 정확히 돌아갔다.
- **두 컴포넌트가 매번 같은 값을 보고했다.**
- 오차가 되돌아온 것이 부작용이 없다는 근거다.
- 단위 테스트 `test_robot_base.py` **13/13** — 우선순위 3단계, 투영, 수직선
  되돌리기, Curve·Vector 받기.

## TRAP-03 .NET 객체에 없는 속성을 넣어도 예외가 안 난다 ★★

- **증상:** `FileWriteOptions` 에 `SaveRenderMeshes=False` 를 넣고 저장했는데 파일
  크기가 그대로였다. 두 번 더 다른 이름으로 시도했고 **한 번도 오류가 없었다.**
- **원인:** 실제 속성은 `IncludeRenderMeshes` 다. 없는 이름으로 `setattr` 해도
  이 파이썬은 조용히 받아들인다 — 객체에 파이썬 속성이 붙고 .NET 쪽은 그대로다.
- **해결:** 넣은 뒤 **읽어서 대조**한다. 값이 안 바뀌었으면 이름이 틀린 것이다.
  실제 이름은 `GetType().GetProperties()` 로 뽑아 확인했다.
- **재발 조건:** .NET 객체의 옵션·설정을 코드로 만질 때마다.
  `try/except` 는 이 실패를 못 잡는다 — 예외가 없는 것이 문제다.

## TRAP-04 임포트로 지운 객체의 재질은 테이블에 남는다 ★★

- **측정:** `test_panels.3dm` 이 106,222 → **584,949 bytes**. 객체 수는 7개로 정상.
  문서 테이블을 세어 보니 **재질 13,776개** = glTF 임포트 4,592 × 3회.
- **원인:** J-007 TRAP-01 에서 임포트 객체는 지웠지만 **재질 테이블은 안 지웠다.**
  `doc.Objects` 만 보고 "원복했다"고 판정한 탓이다.
- **해결:** `_-Purge` + `IncludeRenderMeshes=False`·`IncludePreviewImage=False` 로
  저장 → **77,291 bytes** (원본보다 작다. 객체는 2개 더 많다).
  `import_robot_glb.py` 의 `finally` 에 Purge 를 넣어 재발을 막았다.
- **미확정:** 줄어든 것이 Purge 때문인지 옵션 때문인지 **분리하지 않았다.**
  둘을 같이 넣었고 결과가 충분히 작아 더 파지 않았다.
- **덧붙임:** `doc.Materials.Delete(i, True)` 는 `Delete() takes exactly 1
  argument` 로 실패한다. 재질을 직접 지우는 경로는 쓰지 않았다.

## TRAP-05 못 가는 위치가 "되는 것처럼" 보인다 ★★★

점을 옮겨 위치를 잡아 보니 **동작이 불가능한 자리도 정상처럼 재생됐다.**
사용자가 바로 알아챈 결함이고, 원인이 둘이다.

**1. IK 는 관절 한계에서 잘라낸다.** `solve_ik` 가 수렴하지 못해도 포즈는
나오고, 그 포즈는 **팔이 그럴듯하게 서 있는 자세**다. 롤러만 판재에서 떠 있다.
Play 는 그 포즈를 그리기만 했으므로 화면에 아무 표시가 없었다.

    고친 것 — reach_err 를 받아 화면에 드러낸다
      · 못 닿는 구간에서 로봇 몸체 색을 바꾼다
      · TCP 와 가려던 자리를 붉은 선으로 잇는다 (선 길이가 곧 오차다)
      · 실패 타겟을 경로 위에 X 로 표시한다
      · HUD 에 "도달 실패 668 / 1175 (56.9%) 최대 342 mm" 를 붉게 적는다
      · reach_err 를 연결하지 않았으면 "도달 판정 없음" 이라고 적는다

**구간 오차는 양 끝 중 큰 쪽을 쓴다.** 구간 안은 관절 공간 보간이라 오차가
어떻게 변하는지 모른다 — 낙관적으로 잡으면 고치려던 문제가 그대로 남는다.
**오차를 모를 때 0 으로 채우지 않는다.** `None` 으로 두고 "판정하지 못했다"고
적는다. 모르는 것을 실패로 칠하면 거짓 경고가 되고, 성공으로 칠하면 이 결함이다.

**2. IK 는 간섭을 전혀 모른다.** 베이스를 몰드 위로 옮겨 보니(X +2600)
668/1175 는 실패로 잡혔지만 **나머지 507 개는 "성공"으로 셌다** — 그 자세들은
몸통이 몰드를 관통한다. 캡처를 보면 로봇이 몰드 안에 박혀 서 있다.

전면 간섭 검사는 무겁다. 그런데 **베이스가 몰드 영역과 겹치는 것만은 무조건
불가능**하므로 그것만 값싸게 잡았다 — `robot.base_overlap()`.

- 반경은 **실측**이다: base 파트 바운딩박스 x[-627, 377], y ±360 → 630 mm.
  `test_base_radius_matches_measured_mesh` 가 파일이 바뀌면 걸어 준다.
- 평면상 축정렬 상자 거리로 본다. 회전한 몰드에서는 조금 보수적으로 나온다.
- **z 는 보지 않는다.** 로봇을 내려도 베이스는 같은 자리를 차지한다.
- 화면에 베이스 원을 그리고 겹치면 붉게 칠한다. info 에는 여유(mm)를 적는다.

**남은 간섭은 여전히 안 본다** — 팔이 몰드·강선·핀을 통과하는 것.
실물 메시가 있으므로 이제 가능하지만, 표시용으로 48% 줄인 메시라 판정에 쓰려면
밀도를 다시 봐야 한다(J-007 미해결).

## 미해결

- 점·선으로는 베이스를 **기울일 수 없다**(의도적). 기울기가 필요하면 `robot_base`
  평면을 직접 준다. J-007 미해결의 "베이스 기울기"를 시험할 때 그 경로를 쓴다.
- 베이스 z 를 점의 z 로 받는다. 로봇을 받침대에 올리는 경우는 시험하지 않았다.
- `Param_Point` 가 참조로 붙는 것은 실측했지만, 사용자가 점을 **지우면** 어떻게
  되는지는 확인하지 않았다.
- **팔의 간섭 검사가 없다.** 베이스 겹침만 본다. 몸통·강선·핀 간섭은 미구현.
- 관절 가동범위 접촉(`at_limit`)은 `AMv1 Robot` 의 info 에만 있고 Play 화면에는
  나오지 않는다. 위치 오차가 대개 같이 커지므로 우선순위를 낮게 두었다.
- **좋은 베이스 위치를 자동으로 찾아 주지 않는다.** 지금은 점을 끌어 보며
  숫자를 읽는 방식이다. 사용자가 z 를 -500 으로 내려 실패 10 → 0,
  최대 오차 6.773 → 1.270 mm 를 찾아냈다 — 자동 탐색이 있으면 더 빠를 것이다.
