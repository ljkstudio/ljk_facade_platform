# J-012 · Play 를 셋으로 쪼갰다 — Base / Check / Play

> `AMv1 Play` 가 입력 30 / 출력 9 / 코드 30,420자로 부풀었다. 재생·판정·간섭·
> 베이스 결정을 한 덩어리가 물고 있었다.
> **바뀌는 이유로 갈랐다:** 좌표 규약(Base) · 공학적 판정(Check) · 표시와
> 시간(Play). 결과는 **24 / 15 / 6 입력**이고, 계산값은 한 자리도 바뀌지 않았다.

---

## DECISION-01 경계는 "바뀌는 이유"로 긋는다 ★★

| 컴포넌트 | 손대는 때 | 입출력 |
|---|---|---|
| **AMv1 Base** | 베이스를 어디 세울지, 무엇으로 지정할지 | 6 / 4 |
| **AMv1 Check** | 판정 기준(가동범위·정격속도·여유)이 바뀔 때 | 15 / 9 |
| **AMv1 Play** | 보이는 방식(색·프레임률·무엇을 그릴지) | 24 / 8 |

한 덩어리였을 때는 **색을 고치려다 판정을 깨고, 그 반대도 됐다.** 그리고 판정은
무거운데 재생은 실시간이어야 한다 — 나눠 두면 재생 중에 판정이 다시 돌지 않는다.

**기각 — 2분할(Check / Play):** 변경량이 가장 적지만 베이스 입력 3개(`robot_base`,
`base_pt`, `base_dir`)가 **세 컴포넌트에 중복**으로 남는다. 그 중복이 바로 J-006
TRAP-03(각자 해결하면 오류 없이 서로 다른 자리를 계산)의 온상이다.

**기각 — 4분할(Base / Mech / Hit / Play):** 간섭만 따로 떼면 잠금(토글)을 더
깔끔히 걸 수 있지만, 배선이 늘고 "판정 결과"가 두 곳에서 나와 Play 가 두 입력을
받아야 한다. 판정은 하나의 답으로 나오는 것이 낫다.

## DECISION-02 Base 를 따로 두면 함정이 구조적으로 사라진다 ★★

전에는 Robot·Play 가 각자 `resolve_base_plane()` 을 불렀다. 코드는 한 곳인데
**입력을 둘에 똑같이 물려야 하는 부담**이 남았고, 하나만 빼먹으면 오류가 나지
않고 **로봇이 계산된 위치와 다른 곳에 그려졌다.** 화면은 그럴듯한데 숫자는 다른
자리를 말하는, 가장 찾기 어려운 종류의 버그다.

이제 Base 가 `plane` 하나를 내고 받는 쪽은 **판단하지 않는다.**
안 물리면 아무것도 안 나오거나 로봇이 원점에 서므로 **빼먹은 것이 바로 드러난다.**

**Robot 은 코드를 한 줄도 고치지 않았다.** `resolve_base_plane` 의 우선순위가
`robot_base`(평면) > 점·선 > 자동이므로, **Base.plane → Robot.robot_base 를
물리기만 하면** 기존 점·선 입력은 우선순위에서 밀려 무해해진다. 잘 돌고 있는
컴포넌트를 건드리지 않는 쪽이 항상 싸다.

## DECISION-03 Play 는 판정의 **이유**를 모른다 ★★

Check → Play 로 넘기는 것은 딱 둘이다:

    warn   HUD 에 그대로 띄울 줄 (문장)
    bad    문제가 있는 구간 인덱스 (정수)

Play 는 `bad` 에 든 구간을 다른 색으로 칠하기만 한다 — 도달 실패인지 간섭인지
**구분하지 않는다.** 그래서 판정 기준이 바뀌어도 Play 코드는 손대지 않는다.

**Play 가 문장을 만들지 않는 것도 규칙이다.** 판정 문구를 양쪽에서 쓰면 두
컴포넌트가 서로 다른 말을 하게 된다. Check 가 쓴 줄을 그대로 그린다.

전에 있던 "못 닿는 구간에서 로봇을 붉게" 기능을 잃지 않으려고 이 경계를 잡았다.
기능은 그대로 남고, 판정 논리만 넘어갔다.

## FACT-01 리팩터가 계산을 바꾸지 않았다 (회귀 확인) ★★

**분할의 성공 판정은 "동작한다"가 아니라 "같은 답이 나온다"다.**
같은 입력·같은 베이스에서 분할 전후를 대조했다:

| 항목 | 분할 전 | 분할 후 |
|---|---|---|
| 총 시간 | 587.8 초 | **587.8 초** |
| 관절 최소 여유 | 7.1 (j2) | **7.148112 (j2)** |
| 최소 오버라이드 | 21.5% | **0.21507** |
| 최대 도달 오차 | 1.27 mm | **1.27 mm** |
| 간섭 최소 여유 | 66 mm | **66.36 mm** |
| 이송/관절 지배 | 1066 / 108 | **1066 / 108** |

`ok=True`, `bad` 0개. 코드 길이는 30,420 → **24,025**(Play) + 11,309(Check) +
3,183(Base).

## FACT-02 `warn` 에 통과도 적는다 ★

처음에는 `warn` 을 경고만 담게 했더니 도달 판정이 통과했을 때 **HUD 에서
사라졌다.** 그러면 "판정했고 괜찮다"와 "판정 자체를 안 했다"가 구분되지 않는다 —
이 프로젝트에서 가장 자주 문제가 된 구분이 정확히 그것이다(J-008).

그래서 `warn` 은 경고 목록이 아니라 **HUD 에 띄울 판정 요약**이고 통과도 적는다:
`도달 OK 최대 1.27 mm`. 같은 이유로 `ok` 는 **미판정을 통과로 세지 않는다** —
`reach_err` 를 안 물리거나 `check_hit` 를 끄면 `False` 다.

## TRAP-01 슬라이더·토글은 값만 바꿔도 안 내려간다 ★★

`GH_BooleanToggle.Value = True` 로 바꾸고 컴포넌트를 `ExpireSolution` 했는데
**옛 값으로 계산됐다**(리포트가 "미검사" 그대로). 컴포넌트를 만료시켜도 상류
토글의 `VolatileData` 는 그대로여서 다시 수집해도 같은 값이 온다.

**해결:** 값을 바꾼 **그 위젯을** `ExpireSolution(True)` 한 뒤 문서를 푼다.
**재발 조건:** 브리지에서 슬라이더·토글 값을 바꿀 때마다.
(증상이 "설정이 안 먹는다"라서 코드를 의심하게 만든다 — 실제로는 배선 문제다.)

## TRAP-02 셸 heredoc 이 백슬래시를 한 겹 먹는다 ★★

`param_docs.py` 를 재구성하는 생성기를 셸 heredoc(`python - <<'PY'`)으로 돌렸다.
소스의 `'\\n"'` 가 파이썬에 `'\n"'` 로 도착해, **생성된 파일의 문자열 리터럴 안에
실제 개행이 박혀** 43 KB 정본이 `SyntaxError` 로 깨졌다.

- **1차 방어: 즉시 복원.** `git checkout -- gh_components/param_docs.py`.
  정본이 커밋되어 있었으므로 손실이 없었다. **생성기로 정본을 덮어쓸 때는
  커밋된 상태에서 시작한다.**
- **2차 방어: 백슬래시를 소스에 쓰지 않는다.** `BS = chr(92)` 로 만들어 조립한다.
- **3차 방어: heredoc 을 쓰지 않는다.** 생성기는 파일로 쓰고 경로로 실행한다.

**재발 조건:** 셸을 거쳐 파이썬에 이스케이프를 넘길 때마다.
같은 계열: 브리지 JSON 에 비ASCII 를 태우지 않는 규칙(경로만 넘긴다).

## PROCEDURE-01 분할 순서 ★

1. 새 스크립트를 먼저 쓴다 (Base, Check).
2. 스펙(`SPECS`)에 **Base → Check → Play → Robot 순서로** 넣는다. Base 가 먼저
   생겨야 뒤의 것이 그 출력에 배선된다. dict 삽입 순서가 그대로 실행 순서다.
3. `share` 로 **기존 배선을 물려받는다** — Base 의 `base_pt`/`base_dir` 는 Robot 이
   물고 있던 Rhino 참조를 그대로 받는다. 사용자가 잡아 둔 자리를 잃지 않는다.
4. Play 는 `reorder=True` 로 입력을 다시 만든다(28개 배선을 닉네임으로 복원).
   Robot 은 `reorder=False` — 잘 도는 것을 다시 만들지 않는다.
5. 코드를 넣었으므로 **`apply_param_docs.py`** 를 돌린다 (`--check` 0 차이 확인).
6. 저장 후 **다시 읽어** 컴포넌트 7개·코드 길이·파라미터 수를 센다.
7. **분할 전 숫자와 대조한다** (FACT-01). 이게 없으면 분할을 검증한 것이 아니다.

## 미해결

- **리본 팔레트에 Base·Check 가 아직 없다.** `.ghuser` 는 디스크에 정상 저장됐지만
  (4,920 / 11,056 bytes) 세션 안의 팔레트 레지스트리가 갱신되지 않는다.
  `LoadExternalFiles()` 는 부르면 안 된다 — 모든 User Object 가 새 GUID 로
  중복 등록된다(J-007 실측 6 → 12). **디스크가 정본이고 Rhino 를 다시 켜면
  나온다.** 확인은 다음 세션에서.
- **`AMv1 Check` 의 `ok` 를 아무도 안 쓴다.** 출력만 있고 소비자가 없다. 자동
  탐색이나 배치 검증에서 쓸 자리다.
- **Play 의 `feed`·`joint_scale` 이 Check 와 중복이다.** 시간 계산에 필요해서
  남겼는데, 두 컴포넌트에 다른 값을 물리면 리포트와 재생이 어긋난다. 슬라이더를
  공유하도록 배선했지만 **구조적으로 막혀 있지는 않다.**
- **`bad` 는 구간 인덱스이고 `step>1` 이면 의미가 흐려진다.** Check 가 경고는
  하지만 인덱스를 보정하지는 않는다.
- 컴포넌트가 7개가 되어 캔버스 배선이 늘었다. 지금은 도구가 자동으로 물리므로
  부담이 없지만, 더 늘면 하나로 묶는 클러스터를 고려해야 한다.
